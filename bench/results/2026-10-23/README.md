# Further optimization measurements

See [workload, changes and interpretation](../../../docs/TOWN_BENCHMARKS.md).
`summary.json` aggregates the raw CSVs; all units are milliseconds. Town samples
use seed 1, one warmup, then three samples. GPU samples use one warmup, then five.
The host and GPUs were shared and unpinned; timings are observations, not latency
guarantees. In particular the long town run is close to the previous pass.

Reproduce town runs from the repository root:

```bash
./bench/town.sh --engine rust --players 32,128,1000,10000 --samples 3 --out /tmp/town-scaling
./bench/town.sh --engine rust --players 32,128,10000 --samples 3 --steps 80 --out /tmp/town-lifecycle
```

`town-*/metadata.json` records source hashes, commands, versions and host load;
`fixtures.json` hashes generated fixtures. They are regenerated by the commands
above rather than checked in. Work counters match the previous optimized pass.

Reproduce movement-only GPU runs after `./gpu/nvvm/build-device.sh`:

```bash
AI_TOWN_BENCH_DIR=/tmp/gpu-east AI_TOWN_BENCH_AGENTS=1000,10000 AI_TOWN_BENCH_SAMPLES=5 AI_TOWN_CPU_THREADS=1 cargo run --release --locked --manifest-path gpu/Cargo.toml --bin fair-bench
AI_TOWN_SCENARIO=headon AI_TOWN_BENCH_DIR=/tmp/gpu-headon AI_TOWN_BENCH_AGENTS=1000,10000 AI_TOWN_BENCH_SAMPLES=5 AI_TOWN_CPU_THREADS=1 cargo run --release --locked --manifest-path gpu/Cargo.toml --bin fair-bench
```

The bench locates the built PTX through its standard search path; its explicit
`AI_TOWN_PTX` override can select another build. Before-pass GPU geometry and
allocation implementations are those at base commit
`8e60c408361b89e1a536c317af98dad3a321a856`; other town changes were already present.
`gpu-before/metadata.json` records the exact relevant source hashes. Reproduce
that comparison in a separate checkout using the recorded versions, rebuilding
PTX for each version. Both scenarios check CPU/GPU end placements. The GPU device
algorithm did not change in this pass. Pool cleanup happens at device destruction;
its high-water allocations remain resident across calls, and inputs are reuploaded
every time. These GPU measurements cover movement, not conversations, decisions,
LLM inference or database operations.

`profiling/town-profile.json` is a separate diagnostic run with operation timing.
`profiling/instrumentation.patch` adds six phase timers to a disposable copy of
`kernel/src/rules.rs`. Apply it to the recorded source, run `town-profile` with the
10k fixture and arguments `60 80`, and sum the `PHASE` nanoseconds on stderr.
`phases.json` preserves those totals. Timer/logging overhead is included; the patch
is not applied to production code or the generated Lean extraction.

`validation/` records tests, source hashes, a browser interaction check and a
48-second live UI cadence check. UI pacing is not a frame-rate measurement.

## Tick history comparison

The `history-*` directories are a separate rerun with actual tick recording,
upstream-compatible compression and retained delivery packets in both engines.
See [current measurements](../../../docs/TOWN_BENCHMARKS.md#tick-history-and-playback--2026-10-23).
`history-summary.json` aggregates these results independently of the older
`summary.json`, whose Rust runs did not record motion history.

The short-window comparison uses Rust CSVs from `history-short-rust-final/` and
original CSVs from `history-short/`. Rust was rerun after the codec helpers were
restructured to support Lean extraction; the earlier Rust CSVs are retained for
traceability and excluded from the summary. Upstream sources were unchanged.
`history-lifecycle/` measures both engines at 32 and 128 residents;
`history-lifecycle-10000-rust/` measures Rust at 10,000. Original at 10,000 over
76.8 simulated seconds was not measured. All cases use one warmup, three samples,
seed 1 and 60 ticks per batch. They ran sequentially on a shared, unpinned host;
part of the initial short-window run overlapped Lean extraction/build work.

Each directory has raw CSVs, launch-time source/version/host metadata and fixture
SHA-256 hashes. The generated fixture JSON is omitted and can be regenerated with
`node bench/scenarios/town.mjs COUNT OUTPUT 1`.

```bash
./bench/town.sh --out /tmp/history-short
./bench/town.sh --engine rust --out /tmp/history-short-rust-final
./bench/town.sh --players 32,128 --steps 80 --out /tmp/history-lifecycle
./bench/town.sh --engine rust --players 10000 --steps 80 --out /tmp/history-lifecycle-10000-rust
```

`history-validation/` contains Rust/GPU, JavaScript codec/playback, frontend build,
Lean gate and actual browser validation logs. Its metadata lists commands and
source hashes. The 10,000-resident demo browser check and the 128-resident original
check saw actual history playback with no console/request errors. These are
in-memory checks: no live LLM or PostgreSQL integration was run. Node tests need
Node 22.18+ for native TypeScript stripping; Node 24.21.0 was used.
